## Why this is the right fix: measured, not inferred

The gate's effect is directly observable on the running system. `\_SB.HFRP`
exists as an ACPI object but is inert, while the already-patched `\_SB.SSPM`
is fully enumerated:

```
MTK00055:00  hid=MTK00055  status=0   path=\_SB_.HFRP   <- no physical_node
NVDA3000:00  hid=NVDA3000  status=0   path=\_SB_.SVP0   <- still gated, as designed
NVDA8400:00  hid=NVDA8400  status=15  path=\_SB_.SSPM   <- has physical_node
```

`/sys/bus/acpi/devices/MTK00055:00/` has only `hid/cid/uid/path/status/...` —
no `physical_node`, and no `/sys/bus/platform/devices/MTK00055:00`. With
`_STA = 0` Linux builds the ACPI object but never creates a platform device,
so HFRP's `_CRS` (mailbox `0x311C0000`, doorbells `0x311C0100..010C`,
`0x31270074`, IRQ 0x324) is unreachable by any driver. SSPM, whose predicate
this override already neutralises, does get a platform device. So flipping
HFRP's `status` 0 -> 15 is exactly and only what is needed to make the mailbox
bindable.

The live override is confirmed in place and working on the `-yoga` kernel:

```

ACPI: DSDT 0x0000000080274000 04BDBD (v02 LENOVO CB-01    00000005 INTL 20190509)
/sys/firmware/acpi/tables/DSDT = 06b53baf...  OEM rev 5, 2 gates remaining
```

## What the change is

Three files under `provenance/hardware/`, in the companion diff:

1. **`acpi_builder.py`** — `sspm_sta()` becomes `gated_sta(dsdt, device, hid)`,
   parameterised instead of hardcoded to `NVDA8400`/`SSPM`; a new
   `ENABLED = (("SSPM", b"NVDA8400"), ("HFRP", b"MTK00055"))` table drives
   `patch_dsdt()`, which now patches every listed device. All the structural
   rigour is kept per device: exactly one Device holds that `_HID`, its name
   must match, it must hold exactly one `_STA`, and those bytes must be the
   expected gate. Offsets are still never pinned. Pinned output hashes updated.
   `firmware()` now also recognises the superseded SSPM-only override, so a
   DSDT dumped from a machine booted with *either* override is reported as
   such rather than as "not the DSDT of BIOS SDCN77WW".
2. **`sspm-patch.json`** — single `target` becomes a `targets` list of two,
   plus `supersedes_patched_sha256` and the HFRP rationale. SVP0 stays in
   `other_gated_devices_left_hidden`.
3. **`power-archive.json`** — the two digests that change.

Preferred over `acpi_osi="!Windows 2022"` for the reason the answers file
gives: that would also un-gate SVP0, NH1X and NMAP and change `_OSI` behaviour
platform-wide. This touches two devices and nothing else.

### What this does and does not achieve

Achieved: the mailbox is addressable by a driver. That was the blocker.

Not achieved: anything can actually vote yet. And one thing to flag for the
Windows side, because it changes the shape of the next step — **N1X's HFRP does
not look like MT8196's voter**. MT8196 drives HFRP hardware-voter domains by
direct register set/clr (0x220 set / 0x224 clr / 0x142C done). What ACPI
describes here is a 0x100 region plus **four doorbells and an IRQ**, which is an
IPI mailbox: you compose a message, ring a doorbell, and a coprocessor performs
the vote. That matches `hfrp_ipi_init` in `nvCamsys.sys` rather than a raw
voter. So the next step needs the **HFRP IPI message format**, not a register
map, and the open question from the previous report stands and is now the
critical path:

- Does `MiCode/MTK_kernel_modules` (bsp-dali-v-oss) contain the HFRP IPI
  protocol — command IDs for CAM_VCORE / CAM_MAIN / CSI_BS_RX / CSI_LS_RX, and
  the mailbox layout? If yes, this is a port. If no, it needs a Windows-side
  MMIO/IPI trace of `nvCamsys` at camera start.
- `0x31160000` (ISP1's own 4 KB) is claimed by `NVDA2801:00` and remains the
  other candidate for where the voting actually happens.

No MMIO has been read from either region. On MediaTek SoCs a read of an
unpowered block can hang the bus, so that needs Russ's OK first.

## Next-step research, done on the stick after the reboot (source only, no MMIO)

With HFRP enumerated, I chased how the vote would actually be sent. Four
findings, which together change the plan in the answers file.

### 1. MediaTek's camera voter layout is fully public — but N1X does not expose it

From `mtk-dev-dali/drivers/soc/mediatek/mtk-scpsys-mt6991-mmpc.c`, the
hardware-voter description for every camera domain (all via
`hwv_comp = "mm-hw-ccf-regmap"`, which `mt6991.dts` binds to
`mm_hwv: syscon@31b00000`, 0x6000 long):

| Domain | set | clr | done | en | set_sta | clr_sta | bit |
|---|---|---|---|---|---|---|---|
| `cam-vcore` | 0x0218 | 0x021C | 0x141C | 0x1410 | 0x146C | 0x1470 | 21 |
| `cam-main` | 0x0218 | 0x021C | 0x141C | 0x1410 | 0x146C | 0x1470 | 20 |
| `csi-bs-rx` | 0x0220 | 0x0224 | 0x142C | 0x1420 | 0x1474 | 0x1478 | 5 |
| `csi-ls-rx` | 0x0220 | 0x0224 | 0x142C | 0x1420 | 0x1474 | 0x1478 | 6 |

`csi-bs-rx`/`csi-ls-rx` at set 0x220 / clr 0x224 / done 0x142C, bits 5 and 6,
**exactly match the MT8196 figures** in the previous report — the two
generations agree, so these offsets are trustworthy. Dependency order is
`MM_INFRA1 -> CAM_VCORE -> CAM_MAIN` and `MM_INFRA1 -> CSI_{BS,LS}_RX`, with
MM_INFRA1 voted through `mminfra_hwv: syscon@31a80000` (ofs 0x0100, set 0x0104,
clr 0x0108, done 0x0144, bit 2).

**But none of those ranges exists on this machine.** Searched every live ACPI
table for the little-endian addresses:

```
0x31b00000  mm_hwv        not present in any ACPI table
0x31a80000  mminfra_hwv   not present in any ACPI table
0x31b50000  hfrpsys/mmpc  not present in any ACPI table
0x311c0000  \_SB.HFRP     FOUND (DSDT, x2)
0x31160000  ISP1 extra    FOUND (DSDT)
```

and `/proc/iomem` has nothing in `0x31a8/0x31b0/0x31b5`. So porting
`mtk-scpsys-mt6991-mmpc.c` is **not** the path: the registers it writes are not
handed to the OS here. The firmware deliberately exposes the mailbox instead.

### 2. Conversely, N1X's mailbox is not in MediaTek's sources

`0x311c` and `0x3127` appear **nowhere** in either MediaTek tree (device-modules
or kernel-modules, full path listings and all checked-out sources), and no path
in MT6991's tree mentions `hfrp` outside the `hfrpsys` power-controller. N1X's
HFRP mailbox is NVIDIA/N1X-specific. MediaTek's generic
`drivers/soc/mediatek/mtk_tinysys_ipi.c`, `drivers/mailbox/mtk-mbox-mailbox.c`
and `drivers/misc/mediatek/tinysys_scmi/` are the generic framework (fetched
into `mtk-dev-dali` for reference).

### 3. The template is already in NV-Kernels: `sspm_ci.c`

`drivers/soc/mediatek/sspm_ci/sspm_ci.c` (527 lines, in the local sparse
checkout) is **NVIDIA's own ACPI-matched MediaTek tinysys mailbox client**, and
it is the driver bound to `\_SB.SSPM` on this machine right now
(`/sys/bus/platform/devices/NVDA8400:00/driver -> .../SSPM_CI`). It is the
closest possible model for an HFRP driver: same kernel, same firmware idiom,
same SoC.

```c
static const struct acpi_device_id sspm_ci_acpi_match[] = {
	{"MTKW8400", 0, 0, 0}, {"NVDA8400", 0, 0, 0}, {},
};
#define MBOX_BOX(id, ofs)   (base + (id * 0x10000) + ofs)
#define MBOX_IN_SET(id)     (base + (id * 0x10000) + 0x1000)
#define MBOX_OUT_CLR(id)    (base + (id * 0x10000) + 0x1004)
enum scmi_mtk_protocol        { SCMI_PROTOCOL_TINYSYS = 0x80 };
enum scmi_tinysys_protocol_cmd { TINYSYS_COMMON_SET = 0x3, TINYSYS_COMMON_GET = 0x4,
                                 TINYSYS_POWER_STATE_NOTIFY = 0x5, TINYSYS_SLBC_CTRL = 0x6 };
struct scmi_tinysys_common_set_state { u32 reserv, feature_id, p1, p2, p3, p4, p5; };
struct scmi_msg_t { u32 reserved0, status; u64 reserved1; u32 flags, length, message_header, payload[7]; };
```

The transaction is: take a mutex, wait for `MBOX_IN_SET` to clear, `memcpy_toio`
the SCMI message into the slot, `writel(MAGIC, MBOX_IN_SET)` to ring, then an
IRQ handler reads the echoed header and writes `MAGIC` to `MBOX_OUT_CLR` to
hand the slot back. Note it uses `devm_ioremap()` rather than
`devm_platform_ioremap_resource()` **on purpose** — a comment says several
devices share the memory resource — which will matter for HFRP too.

`TINYSYS_COMMON_SET`/`_GET` corroborates the answers file's `nvpep.sys` strings
`DMF_Scmi_Tinysys_Common_Get`/`_Set`: same protocol, different coprocessor.

### 4. `power_wrap` confirms the camera is on its own

`inc/power_wrap.h` defines only three control types —
`CTRL_NONE = 0, CTRL_BY_PWRAP = 1, CTRL_BY_SCMI = 2`. There is no
`CTRL_BY_HFRP`. So ISP1's `CTRL_NONE` is not an oversight to work around: the
power_wrap framework genuinely has no route for the camera, and the camera
driver voting for itself over HFRP is the intended design, exactly as
`nvCamsys.sys` does it.

### Revised plan, and the one thing still missing

The shape of the work is now: write an **`hfrp_ci`-style driver modelled
directly on `sspm_ci.c`**, matching ACPI `MTK00055`, taking HFRP's `_CRS` as
slot region + doorbells + IRQ, and speaking SCMI-over-tinysys to the HFRP
coprocessor. HFRP's resource layout differs from SSPM's in a convenient way —
SSPM has one window with a 0x10000 stride and doorbells at +0x1000/+0x1004,
whereas HFRP enumerates its **doorbells as four separate 4-byte MEM resources**.
**Correction to an earlier draft of this report:** the `_CRS` order is *not*
address order, so the doorbells are MEM indices **2..5**, not 1..4 — the
template lists the IRQ first, then `0x311C0000`, then **`0x31270074`**, then the
four doorbells:

```
Interrupt(...)        { 0x00000324 }
Memory32Fixed(RW, 0x311C0000, 0x100)   <- MEM 0  slot region
Memory32Fixed(RW, 0x31270074, 0x004)   <- MEM 1  (NOT a doorbell)
Memory32Fixed(RW, 0x311C0100, 0x004)   <- MEM 2  doorbell
Memory32Fixed(RW, 0x311C0104, 0x004)   <- MEM 3  doorbell
Memory32Fixed(RW, 0x311C0108, 0x004)   <- MEM 4  doorbell
Memory32Fixed(RW, 0x311C010C, 0x004)   <- MEM 5  doorbell
```

`/proc/iomem` prints these address-sorted, which is what misled the earlier
draft; `platform_get_resource()` follows `_CRS` order.
The 0x100 slot region is two 128-byte mailboxes, and four doorbell words is
consistent with 2 channels x {set, clr} — MediaTek's generic mbox uses
`MBOX_CHANS 2` and `FIXED_MBOX_SIZE 128`, and `sspm_ci` uses
`SSPM_MBOX_NUM 2` with a SET and a GET channel. **That mapping is inference
from layout congruence, not verified.** `0x31270074` is unexplained; in
`mtk-mbox-mailbox.c` the analogous out-of-band register is a secure-mode
mailbox clear (`sspm_do_mbox_clear` via SMC).

**Still missing, and now the only blocker: the HFRP `feature_id` and parameters
for a camera power vote.** The framing is known; the payload is not. Ask of the
Windows side, sharpened:

1. In `nvCamsys.sys`, what does `hfrp_ipi_init` set up, and what
   `feature_id`/`p1..p5` does `__qof_mtcmos_raw_voter` (and
   `mtk_cam_vcore_probe` / `qof_ddren_setting` /
   `update_sen_expo_qof_voter`) send? A `scmi_tinysys_common_set_state`-shaped
   payload is what to look for. This is the single thing that unblocks the
   camera.
2. Does `nvCamsys` use the ACPI `MTK00055` resources, or does it reach the
   mailbox through ISP1's `0x31160000`? Windows enumerates no `MTK*` device, so
   presumably the latter — in which case `0x31160000` may be an alias of the
   same doorbells, and which one Linux should use is an open question.
3. Confirm whether HFRP's `0x31270074` is a secure-clear register (an SMC), as
   the MediaTek analogue suggests.

Nothing here has touched MMIO. Reading either region still needs Russ's OK
(an access to an unpowered MediaTek block can hang the bus), though the mailbox
is a plausible exception since a coprocessor mailbox is normally always-on.

## ACPI leads are now exhausted (read-only, post-reboot)

Checked whether the vote could be discovered or performed through ACPI alone.
Five negative results, all definitive, so nobody repeats this:

1. **`\_SB.HFRP` has no protocol data.** Its entire device body is `_HID`,
   `_CID` (both "MTK00055"), `_UID` (0), `_CRS` and `_STA`. No `_DSM`, no
   named buffers, no methods. (A `PGID` buffer seen near it in an earlier
   disassembly belongs to the *next* device, not HFRP.)
2. **`\_SB.ISP1._PS0` and `._PS3` are empty methods.** ACPI performs no camera
   power sequencing whatsoever; `_S1D/_S2D/_S3D` just return 3.
3. **No AML window onto the relevant MMIO.** All 22 `OperationRegion`s in the
   live DSDT were enumerated; none targets `0x31xxxxxx`. So the mailbox and the
   MT6991 voter registers are unreachable from AML — there is no way to make
   firmware do the vote on our behalf.
4. **ISP1's tables are clocks and LARB ports only** — `CISP` (clock name -> ID),
   `CLRA/CLRB/CLYA/CLYB/CLSA/CLSB/CLM0/CLM2/CLV0/CLV1/CLV4/CLUI` (per-engine
   clocks) and `LPRA/.../LPUI` (LARB ports). No power-domain or feature-id
   table.
5. **`power_wrap` has no HFRP route** — `inc/power_wrap.h` defines only
   `CTRL_NONE = 0`, `CTRL_BY_PWRAP = 1`, `CTRL_BY_SCMI = 2`. ISP1's
   `CTRL_NONE` is by design, not an omission. (`\_SB.PEPD` NVDA6210 is bound to
   `mtk_pwrap` and exposes `pwrap_dev_config_query`, `pwrap_power_ctrl_req`
   etc. in sysfs, but ISP1 is not a client.)

Conclusion: the remaining unknown cannot be recovered from this machine's
firmware. It is either the Windows driver's payload, or discoverable by
experiment against the live mailbox.

## Live mailbox experiments (2026-11-21 ~13:45-13:53, with Russ's explicit OK)

Russ authorised unrestricted testing short of permanent hardware damage. All of
this was done on the live machine. **It caused no damage and no regression** —
after it all: no SError, external abort, oops or unhandled fault anywhere in
dmesg, no ext4 or I/O errors, Plasma/SDDM still up, audio still 2 cards, Wi-Fi
up, 2TB drive still mounted.

### The big win: the wire format is confirmed from a live capture

Reading SSPM's **in-use** mailbox slot at `0x1c8b0000` (via `/dev/mem`, with
SSPM_CI actively driving it) caught a real message in flight. Decoded against
`sspm_ci.c`'s structs it is exact:

```
flags          = 0x00000001
length         = 8
message_header = 0x03ee0003
   message_id   = 0x03  TINYSYS_COMMON_SET
   message_type = 0     COMMAND
   protocol_id  = 0x80  SCMI_PROTOCOL_TINYSYS
   token        = 0x0fb
payload (struct scmi_tinysys_common_set_state):
   reserv = 0x0, feature_id = 0xd, p1 = 0x1c, p2 = 0x04000000, p3 = 0x2
```

So the N1X tinysys power protocol is no longer inferred, it is observed:
`message_header = msg_id | type<<8 | protocol<<10 | token<<18`, payload at
slot+0x1c, `feature_id = 0xd` for device power control.

Cross-checked against `power_wrap`'s live DPMT config
(`/sys/devices/platform/NVDA6210:00/pwrap_dev_config_query`, write a path then
read it back):

| device | control_type | feat_id | dev_id |
|---|---|---|---|
| `\_SB.USB0/1/2` | 2 CTRL_BY_SCMI | 0xd | 0x0 / 0x1 / 0x2 |
| `\_SB.DSP1/2/3` | 2 CTRL_BY_SCMI | 0xd | 0x19 / 0x1a / 0x1b |
| `\_SB.ISP1/ISP2` | **0 CTRL_NONE** | 0x0 | 0x0 |

with `data` rows `[0x1000000..0x5000000, 0, 0, 0]` = the five device states.

**Note the live message used `dev_id = 0x1c`, which ACPI's DPMT does not list
at all** (DSP3 is 0x1b). The SSPM firmware's device namespace is therefore
larger than ACPI exposes — worth remembering, though it does not help the
camera directly, since the camera is on HFRP.

A hazard found while considering SSPM probing, recorded so nobody tries it:
`sspm_ci_set()` is `EXPORT_SYMBOL`'d and callable from a module, but it is
**SET only** (no GET is exported), and `feat 0xd` `dev_id` 0x0/0x1/0x2 are
USB0/1/2 — and this stick boots from USB. Blind SET-probing of the SSPM
dev_id space can cut the root filesystem out from under the machine. Not done.

### `hfrp_ci` experimental driver: written, built, loaded, bound

Source: `/root/src/yoga9n-hfrp/hfrp-ci.c` (313 lines, also archived on the 2TB
drive). Modelled on `sspm_ci.c`; ACPI match `MTK00055`; sends nothing at probe;
all experiments driven from `/sys/kernel/debug/hfrp_ci/{dump,send}` with
`ring_db`/`ack_db` module parameters.

It bound first try and **confirmed the corrected `_CRS` ordering**:

```
hfrp_ci MTK00055:00: slot   [mem 0x311c0000-0x311c00ff]
hfrp_ci MTK00055:00: aux    [mem 0x31270074-0x31270077]   <- MEM 1, not a doorbell
hfrp_ci MTK00055:00: db[0]  [mem 0x311c0100-0x311c0103]
hfrp_ci MTK00055:00: db[1..3] 0x311c0104 / 0108 / 010c
hfrp_ci MTK00055:00: irq    274
```

Also corrects the earlier guess in this report about the IRQ number: virq 274
has `hwirq 804` = 0x324, correct — but **virq is not a fixed offset from the
GSI**. It is allocated dynamically (here virq 265 -> hwirq 542, virq 275 ->
hwirq 530), so the "expect Linux ~548 by the -256 offset" reasoning earlier in
this report was wrong. Read `/sys/kernel/irq/<virq>/hwirq`, never arithmetic.

### What the mailbox actually did — and the honest reading

1. **The block is powered and live.** Every HFRP region reads cleanly with no
   abort: the 0x100 slot, all four doorbells and the aux register were all
   `0x00000000` — idle, never used this boot.
2. **The slot SRAM is writable** and retains what is written, so composing a
   message works.
3. **Doorbell 0: nothing.** No interrupt, no reply.
4. **Doorbells 1, 2 and 3 assert our own level IRQ** (hwirq 804) and my handler
   could not clear it — 3 writes produced a **1975-interrupt storm** before it
   settled. So db1-3 sit on the inbound (coprocessor -> AP) side, or are
   IRQ trigger/status registers; writing them interrupts *us*, not the
   coprocessor. The likely TX doorbell is db0.
5. **No coprocessor ever replied.** This is the key negative, and I initially
   misread it: the `status=0x00000000` and `payload[1]=0xd` I first took for an
   ack were **my own written bytes read back** out of our own slot, and the
   repeated "reply header" log lines were the storm, not messages. After every
   attempt the slot still held exactly what was written
   (`hdr=0x00160004`, `payload[1]=0x0d`), unmodified by firmware. Nothing
   consumed anything.

### What that means, and the revised ask

The transport is reachable, but **the HFRP coprocessor appears dormant** — it
is not servicing its mailbox. That reframes the missing piece as potentially
bigger than a `feature_id`: it may be coprocessor bring-up, not just a message.
On Windows, `nvCamsys.sys` calls `hfrp_ipi_init` *before* any vote, and that may
load firmware onto HFRP or register IPI channels with an already-booted one.

Revised questions for the Windows side, in priority order:

1. **Does anything load firmware onto HFRP, or is it booted by UEFI?** Look for
   an HFRP firmware blob shipped with the NVIDIA/MediaTek driver package, a
   `*.img`/`*.bin` referenced by `nvCamsys.sys`, or a reset/boot register write.
   If HFRP needs firmware, Linux needs that blob and its load procedure — this
   now outranks the feature_id question.
2. **What exactly does `hfrp_ipi_init` do** before the first message —
   which registers does it touch, in what order, and does it write
   `0x31270074` or anything outside the ACPI `_CRS`?
3. **Which of the four doorbells is AP->HFRP**, and what value is written?
   (db0 is the candidate here; db1-3 raise the AP's own IRQ.)
4. Only then: the `feature_id`/`p1..p5` from `__qof_mtcmos_raw_voter`.

Alternative worth testing on Linux first, now that the driver exists: HFRP may
be dormant only because nothing has *started* it, and `0x31270074` (the one
register outside the mailbox block) is the obvious candidate for a reset or
enable. It read 0 throughout. Writing it is the next experiment, and is the
sort of thing that needs a deliberate decision rather than a sweep.

### Supporting evidence for the dormancy hypothesis

`linux-firmware-mediatek` (held, 138 files) ships **`scp.img` System Companion
Processor firmware** for mt8183, mt8186, mt8188 (+`scp_c0`), mt8189, mt8192 and
mt8195. So on MediaTek SoCs these coprocessors are normally brought up by an
OS-loaded firmware image. There is **no mt8901/mt8991 entry and no HFRP blob**,
and the kernel requested no such firmware this boot. Combined with HFRP's
registers all reading zero and its mailbox going unanswered, the most likely
explanation is that **HFRP has no firmware running**, and that whatever loads it
ships with the Windows driver package on the encrypted C:.

If that is right, the camera needs an HFRP firmware image plus its load
procedure, which makes question 1 above the real blocker, not the feature_id.
